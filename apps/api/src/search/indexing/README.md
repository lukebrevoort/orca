# Queued search indexing v3

Migration 0051 installs only ID/version capture. It defaults both readers and workers to disabled and paused. There is no startup backfill, index creation, worker loop, or activation. Experimental PR224 schemas are refused without modification; they need a separately reviewed migration path. Never apply these instructions to real data as part of this draft's verification.

## Files and query contract

The canonical database remains authoritative. `schema.ts` supplies typed readers, format/build identity checks, ASCII-only text normalization, a server-created account/incarnation scope key, and the default sidecar path `<canonical>.search-v3.sqlite`. An index file must be separate from the canonical file. All entrypoints resolve symlinks to a consistent SQLite/WAL path before opening it; canonical and derived files with multiple hard links are refused. `metadata_fts` and `full_fts` are contentless positional trigram indexes; the document map retains independent applied versions, deletion markers and source byte sizes. Scope keys must be excluded from user-text column clauses. Queries must verify each account/mode's exact canonical revision, incarnation, build, ready flag and canonical ownership in pinned snapshots.

Canonical supporting indexes contain IDs and scheduling fields only; there is no canonical FTS or copied search text. Creating the (account_id,id) baseline index needs planned migration time on a large existing mailbox. Claims inspect at most 32 indexed pending IDs under a short transaction, and persist a round-robin account cursor. Delayed work in that bounded probe can defer a later eligible job until the next demand run. All canonical email writes atomically capture an obligation. Metadata field updates dirty both modes; body-only updates dirty full search; identical writes conservatively create a new revision. Jobs contain IDs and control data only. Baseline batches enqueue version zero with conflict-do-nothing and checkpoint in the same short transaction. NULL means an unapplied derived version, so baseline zero is real work. Account disconnect keeps durable account/incarnation cleanup jobs outside cascaded foreign keys. Cleanup deletes at most eight posting rows per attempt and preserves version/tombstone maps. Account ID reuse creates a distinct incarnation.

## Bounded execution and durability

`new SearchIndexSupervisor({canonicalPath}).kick()` does one bounded demand-started run. It creates one child per attempt, at most 16 jobs, 20 seconds of scheduling per run, a 5-second timeout per child, and three attempts with bounded exponential backoff. An in-flight attempt may finish after the run's scheduling deadline. A child opens canonical SQLite readonly/query_only and only the derived file writable. The supervisor performs short claim/ack/failure writes; it acknowledges only an exact build/version/attempt receipt after the child's durable commit and confirmed exit. Coalesced newer jobs survive stale receipts and failures.

Before selecting source text, a read snapshot checks SQLite byte lengths. Default admission is 32 KiB metadata and 256 KiB total full-search text per message. Oversize jobs become explicitly blocked; content is never truncated, dropped, or acknowledged complete. These are provisional defensive bounds, not measured capacities. A single blocked full job keeps that account's full search updating; metadata can continue independently. Queue storage is bounded by unique account/incarnation/message/mode obligations rather than by a fixed maximum mailbox size. A full queue cannot be silently dropped. Tombstones are retained until an explicit rebuild.

Both sidecar connections and the supervisor set WAL/FULL. All canonical writers must also set synchronous=FULL: it is connection-local. Host/power-loss durability on the deployed filesystem has not been validated. Loss of an acknowledged sidecar, a canonical restore, or a source identity mismatch requires a fresh build and full baseline; an empty queue cannot reconstruct lost acknowledgments.

The Linux supervisor samples child RSS every 20 ms and kills above 192 MiB. This watchdog can overshoot and is not a hard memory limit. A per-worker/container cgroup limit, adequate canonical/index/WAL storage, and deployment CPU/I/O isolation remain rollout gates. Non-Linux execution requires an explicitly configured external memory bound. No production capacity, latency, power-loss, or completed security-review claim is made.

## Exclusive ownership and shutdown

Ownership lasts for one active drain (or explicit maintenance operation); an idle supervisor object holds no ownership. An atomic mode-0700 directory at `<sidecar>.writer-lock` and a persistent random sidecar owner token jointly protect each file. Existing directories or tokens are never reclaimed by elapsed time or PID guesses. Every apply/publication transaction checks the token. A second supervisor is refused. Canonical ingestion and Inbox continue while indexing is owned or blocked.

Orderly shutdown stops scheduling, kills the known child, awaits its exit, clears its recorded PID, then clears the sidecar token and removes the directory. Timeout replacement follows the same kill/reap sequence. The host must await `shutdown()` on SIGTERM/SIGINT and allow that shutdown to finish before redeploying. No unowned PID is ever signaled.

A whole-supervisor crash may orphan its child and leaves a stale directory/token. This intentionally blocks replacement until an operator confirms all supervisors and recorded children for that volume have stopped. PID existence alone is not proof of identity or exit; PID reuse must result in refusal, never killing an unrelated process. Inspect the owner record and deployment process/container state. The safe recovery procedure is to stop the whole indexing deployment, verify its children have exited, and retain a copy of the owner record before manually clearing the matching token/directory. There is deliberately no automatic `unlock` command. If stop/exit cannot be established, do not clear ownership or start a new build. Railway/shared-volume deployments must enforce this lifecycle; advisory ownership and ordinary local tests do not prove their container teardown behavior.

## Explicit operator recipe

Run `bun apps/api/src/search/indexing/admin.ts COMMAND /absolute/path/orca.sqlite` only against an explicitly selected database. Take a consistent canonical backup and reserve storage first.

1. `status` inspects capture/baseline/queue state. `init` creates a fresh disabled build and resets baseline checkpoints, refusing an existing sidecar or lock. It never drops mail.
2. Repeat `backfill [accountId] [metadata|full]` until each baseline is complete. Each invocation enqueues at most 64 IDs per account/mode atomically; live capture remains active throughout.
3. `resume` explicitly permits workers. Repeated `drain` commands perform bounded runs; their receipts report attempted/acknowledged/blocked/sealed counts. Pending/delayed/claimed/blocked jobs all prevent readiness. `retry accountId mode` explicitly resets blocked jobs only after their cause is understood.
4. `verify` performs sidecar FTS integrity commands and checks exact readiness for every active account/mode plus zero outstanding work. This is explicit maintenance and can take time on a large derived file. Publication itself proves completed baseline, zero obligations and exact source revision with unchanged mutation token. Mutation clears readiness in the same sidecar transaction as posting changes.
5. Only after deployment isolation, storage/durability, security-review and rollout gates are resolved, `enable` activates reads if every mode is ready. Every query still rechecks exact snapshot equality; a later write immediately makes stale published revisions unusable.
6. `disable` disables indexed reads. `pause` stops scheduling new attempts after any current bounded child; await supervisor shutdown for a hard stop. Capture continues cheaply.
7. Rebuild: disable, pause, stop/reap all supervisors and readers, and verify no surviving owner. Archive the derived sidecar and its WAL/SHM consistently (never canonical mail), then use `init`, baseline, drain, verify and explicit enable again. Do not rename/delete a live SQLite file, clear a stale lock blindly, or reuse an old build after restore. If ownership is stale, complete the confirmed-stop recovery above first.

Status exposes queue state/counts, oldest work, attempts, mode and account progress. Missing readiness is an updating state, never a partial successful result. The safe rollback is disabled indexed reads plus the prior compatible reader release; it does not restore old canonical mail or delete queue obligations.
