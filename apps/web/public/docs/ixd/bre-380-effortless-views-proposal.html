A useful view before you learn a filter.

Describe what you want, start with a few messages, or keep a useful search. See the matching mail. Adjust it. Save it.

Built from the owner's direction: mail should get attention on the user's terms. Names, grouping and attention preferences remain malleable. This milestone removes the friction in creating views; scheduling and notification policies follow separately.

Walk the whiteboard

  1. Three starts, one destination. Describing, selecting, and searching are entry points into one editable draft. They do not become three independent configuration systems.
  2. Mail is the feedback. The preview shows real results and the interpretation that produced them. A name is suggested after useful results appear.
  3. Corrections are visible. A wrong match opens a proposed filter change. Show the consequences, refresh the preview, and allow undo.
  4. Saving is a small commitment. Keep a live query, make it discoverable, and let the user rename or revise it. Do not silently move mail or enable notifications.
  5. One deep module pays back across callers. Human controls, assistant proposals, search, and selection use the same draft and validation. Existing Organization authority stays responsible for mutations.

A deep module, not another filter system

Place the authoring seam next to the existing Views module. Its interface gives callers a draft, a truthful preview, and one explicit commit path. Parsing, supported-query checks, account resolution, readable explanations, digest handling, and mutation handoff live behind it.

ViewAuthoring interface — proposed, not implemented

propose(scope, input, currentDraft?) → Proposal
preview(scope, definition, page?)   → Preview
commit(scope, reviewedDraft, expectedRevisions, retryKey) → View

Input = description | selected thread references | supported search
Proposal = draft | focused clarification | unsupported / unavailable
Draft = suggestedName + definition + interpretation + assumptions
Preview = definitionDigest + effectiveAccounts + matches + cursor
          + provenance (live / fixture) + refreshedAt

Human controls can edit the typed definition without a model.
Discard is local: an unsaved draft creates no database object.
Commit delegates to existing create/update and rechecks authority.

Depth: without this module, each entry point would repeat scope resolution, translation, preview state, and save consistency. That is the deletion test: removing it would spread real complexity across callers.

Locality: extend the query evaluator inside views/; use one web draft owner rather than duplicating orchestration across layouts. An internal interpreter adapter can have production and deterministic fixture implementations. Do not introduce generic plugin abstractions before a second real adapter is needed.

Test through the interface: exact preview/commit definition equality; changed-mailbox results may differ; stale cursors cannot cross definitions or scopes; no writes during proposal/preview; revoked capabilities fail at commit; retries do not duplicate saves; untouched advanced filters survive refinement.

A digest identifies the definition reviewed, not a guarantee that the mailbox is frozen. The server validates every commit again; a preview is never an authority grant.

Implementation slices

BRE-380 · Choose the interaction and settle the contract

Review A/B/C with the owner. Produce an approved journey and copy from this study. Set the supported intent/search vocabulary, correction scope, assistant runtime, and usability threshold before marking dependent drafts ready. The earlier BRE-321 spec changes only where the approved authoring interaction replaces exposed rule concepts; shell, theme and authority requirements remain.

BRE-381 · Unsaved matching-mail preview

Own shared preview schemas, the Views module, query evaluator, read-only preview route, and web draft state. Proposed route: POST /v1/organization/views/preview with a definition and page limit. Reuse existing query capability checks. Saved and unsaved queries share evaluation. Cursor keys include authorized scope and definition digest. No temporary persisted views; commit delegates to create/update with existing revisions and idempotency.

BRE-382 · Intent and conversational refinement

Own proposal interpretation and the description adapter into the draft. A typed output is validated against supported view semantics and account/resource scope; derive the readable explanation from that definition. Supported structural requests can preview directly; ambiguity returns one focused question; unavailable assistance returns to manual filtering. “Apartment hunting” must not be presented as semantic classification if the actual filter is only a subject substring. Runtime choice remains a named pre-implementation decision.

BRE-383 · Selected-mail entry

Own selection handoff and example-based proposals. Use account/thread references and server-resolved evidence; never turn a page of selected IDs into a pretend live query. Show matches beyond the examples. For a deterministic initial fallback, offer sender-set matching with a visible scope explanation. Preserve list position and selection on cancel.

BRE-384 · Search entry

Own exact search-to-view translation and Save as view entry. Establish a supported translation matrix against mailbox reader semantics. Unsupported body/general text or attention filters must be explained rather than dropped. The prototype's search is explicitly subject-only and does not validate production search equivalence.

BRE-385 · Correction and customization

Own saved-view edit, rename, order, removal and correction presentation. Patch the full typed definition; preserve opaque advanced fields. First slice offers explicit narrowing and preview/undo. Per-thread exclusions are not in the current schema: add a bounded, account-aware exclusion contract only if selected in BRE-380, with evaluator, revision, cursor and regression coverage. Do not secretly encode membership in a live view.

BRE-386 · First useful view guidance

Own the skippable invitation and contextual next-step help. It invokes the same three production entry points and save path. Store dismissal at the approved preference scope during implementation; the prototype uses memory only. Avoid a separate tutorial engine or mandatory setup.

BRE-387 · Acceptance evidence

Own the uncoached usability study, repeatable mail fixture and HTML validation guide. Proposed target for owner review: at least four of five participants independently create a useful view in 60 seconds and correct a wrong match. Record preview latency separately. Use real human evidence; a runnable prototype is not usability validation. Exercise account scope, unchanged mail/policy state, current/future results, keyboard and theme states.

Sequence: 380 → 381 → 382 / 384 → 383 / 385 → 386 → 387. Search can ship before assisted creation. All issues remain draft / needs-triage pending design feedback; no implementation is claimed complete.

Evidence and limits

Browser walkthroughs passed for description, correction, undo, save, selection, search, rename, unavailable assistance, manual fallback and empty results. Three layouts were checked in light/dark at 1440 and 1024 pixels with no horizontal document overflow. Selected controls retain text. Web typecheck and production build passed; the existing large-bundle warning remains.

The prototype uses six static sample messages, constrained phrase recognition, in-memory filters/saves, and the existing demo shell. It does not exercise real model latency, account isolation, database persistence, production search translation, first-use preference persistence, concurrency or notification behavior. No human usability verdict exists yet.
