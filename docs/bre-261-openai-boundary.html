Orca M6 · BRE-261 · Architecture decision

ChatGPT visits Orca. Orca does not become ChatGPT.

M6 supports “Use Orca from ChatGPT or Codex” through a revocable, OAuth 2.1-protected, read-only Orca resource. It does not treat a ChatGPT subscription as API credit, store an OpenAI key, run a model in the background, or let model output mutate a mailbox.

Selected boundary ChatGPT/Codex is the OAuth client. Orca is the authorization and resource boundary. The existing Orca sign-in authenticates the person; a narrow OAuth authorization layer issues account- and scope-bound Orca grants. The remote client receives only the result of four read operations after live ownership checks and explicit redaction.

Three directions considered

✓

External host → Orca

Supported for M6. ChatGPT/Codex connects to a read-only Orca MCP resource with OAuth 2.1 and per-account consent.

×

Orca → OpenAI API

Deferred. This requires a separately billed API provider, retention decision, rate limits, operational isolation, and a new user promise.

×

“Sign in with ChatGPT”

Rejected for M6. There is no product promise that ChatGPT identity or subscription entitlement powers Orca jobs.

Never crosses this boundary

  • Gmail/Outlook access or refresh tokens, Orca sessions, cookies, authorization headers, OpenAI keys, or ChatGPT credentials.
  • HTML bodies, remote images, raw provider payloads/headers, BCC, attachment bytes/URLs, drafts, or unrelated contacts/accounts.
  • Send, draft, archive, delete, relabel, mark read, change attention, or agent-event lifecycle actions.
  • Instructions contained in email. Mail is untrusted data, never authority to invoke another tool.

Authorization flow

1 · ClientChatGPT or Codex discovers Orca’s protected resource metadata and starts authorization with the exact resource, requested read scopes, redirect URI, state, and PKCE S256 challenge.
2 · Orca consentThe existing signed-in Orca session identifies the user. Orca shows scope copy and only that user’s currently connected accounts. Approval creates a revocable Orca grant.
3 · BearerThe authorization-code exchange yields a ≤10-minute access token and a rotating refresh token valid no longer than 30 days. The access context binds issuer, resource/audience, user, accounts, scopes, issue time, and expiry.
4 · ResourceEvery call verifies the token and active grant, intersects claimed accounts with current ownership, authorizes a contract operation, then applies its allowlisted output projection and redaction.

IssuerThe exact credential-free HTTPS issuer configured as ORCA_M6_MCP_ISSUER. M6 reuses Orca’s established sign-in identity and implements only the narrow authorization layer needed to mint Orca grants. No alias or fallback issuer is accepted.

Redirect URIs are registered and matched exactly; HTTPS is required except loopback development callbacks.

Token and account rules

  • iss equals the configured issuer; aud and OAuth resource equal the canonical resource.
  • sub maps to exactly one Orca user. Account claims are an explicit subset selected at consent.
  • The resource server intersects token accounts with live DB ownership on every request. A disconnected or transferred account stops working immediately.
  • Access tokens live no longer than 600 seconds. Refresh tokens rotate on every use, expire within 30 days, and replay revokes the connection.
  • Scope expansion, adding accounts, changing the resource/issuer, expiry, or revocation requires a fresh authorization flow. Refresh may only preserve or narrow a grant.
  • Orca stores grant/revocation state and only hashes of its own opaque refresh tokens. It stores no ChatGPT credential or user OpenAI API key.

Consent, reauthorization, revocation

Consent copy must name the client, selected Orca accounts, and each requested exposure in plain language. It must say that message data will be sent to ChatGPT/Codex and that Orca cannot control the client’s downstream retention.

Users can revoke one connection or all connections in Orca. Revocation blocks active access tokens at the grant check and invalidates refresh-token families. A client reconnects through the complete consent flow; there is no silent re-grant.

Redaction policy

Projection is allowlist-first: unsupported fields never enter the result. A second pass redacts sensitive key names and credential-shaped values such as bearer tokens, JWTs, OpenAI-style keys, Google tokens, cookies, passwords, and client secrets. Text is stripped of control characters and bounded to 20,000 characters per field.

Redaction is defense in depth, not a claim that arbitrary email can be made non-sensitive. The user’s explicit content scope remains the authorization for exposing message text.

Deferred Orca-hosted runtime

BRE-276 must separately decide provider and model, who owns billing, whether credentials are Orca-managed or user-managed, provider retention/ZDR requirements, rate/cost limits, prompt/data minimization, tenant isolation, logging, deletion, failure behavior, and evaluation. Until then model_assisted is a contract placeholder, not an enabled execution path.

Official OpenAI documentation says API data is not used for training by default, while abuse-monitoring and endpoint application-state retention can still apply. That is why this decision does not equate “not trained on” with “not retained.”
