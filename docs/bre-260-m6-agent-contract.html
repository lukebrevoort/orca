Orca M6 · BRE-260 · Contract v1

Keep the timeline calm. Propagate the machine mail that matters.

M6 adds an explainable, local projection over normalized mail. It does not replace Human Signal, silently change attention, mutate Gmail or Outlook, or turn a ChatGPT subscription into an Orca model runtime.

The product promise

Orca remains the source of truth for normalized mail, account ownership, Human Signal, and user attention choices. An agent may create a short, source-linked event when an automated message has a concrete consequence. The original message stays in Tideline and the projection stays reversible.

Four independent answers

Human Signal

How does Orca estimate the message was produced?

automated_or_bulk

Attention

Where did the person choose to place this sender?

normal

Agent importance

Does this specific event have a likely consequence?

high

Propagation

Should a local explanation appear somewhere else?

timeline

None of these fields may be inferred from another. “Automated” does not mean unsafe or unimportant. “Propagated” does not move the source out of Tideline or change provider state.

End-to-end flow

1 · IngestGmail push/sync or future Outlook sync stores normalized mail.
2 · ClassifyM5 computes the independent effective Human Signal result.
3 · AssessA post-classification agent evaluates conservative local policy.
4 · ProjectRetry-safe storage upserts a short event or suppresses it.
5 · InspectOrca UI renders locally; optional OAuth-scoped MCP reads it.

A propagation failure is isolated: normalized mail and Human Signal still commit. ChatGPT/Codex is not in the ingestion path and no OpenAI credential is needed for steps 1–4.

Trust boundary

  • Email subject, body, headers, links, and attachments are untrusted content—not instructions, policy, authorization, or tool calls.
  • Store a bounded derived title/summary/reason plus source IDs. Do not duplicate full bodies into the event row.
  • Ordinary logs contain IDs, rule/version, reason codes, disposition, and latency—not bodies, tokens, authorization codes, secrets, or API keys.
  • No send, draft, archive, delete, relabel, provider navigation, or provider write exists in M6 MCP or lifecycle actions.

ChatGPT/Codex integration decision

M6 means “Use Orca from ChatGPT/Codex.” ChatGPT or Codex acts as an OAuth client of Orca’s read-only remote MCP resource. Orca does not “sign in with ChatGPT,” consume a ChatGPT subscription for background work, store a ChatGPT credential, or require a user OpenAI API key.

ClientChatGPT / Codex requests Orca tools.
AuthorizeOAuth 2.1 authorization code + PKCE S256 and explicit consent.
BindToken verifies issuer, exact resource/audience, user, account allowlist, scopes, issue/expiry, and revocation.
ReadHTTPS streamable MCP serves bounded Orca projections only.

The production resource identifier is the canonical HTTPS MCP endpoint, https://<deployment-origin>/mcp. The authorization server issuer is deployment configuration and must exactly match discovery metadata. Access tokens live at most 600 seconds. Reauthorization and revocation are explicit. Refresh-token storage, if selected downstream, must be encrypted and connection-scoped.

Resource capabilities

  • orca:mail.metadata:read
  • orca:mail.content:read
  • orca:agent-events:read
  • orca:connection-status:read

These are internal tool capabilities. BRE-267 maps public OAuth mail:read to mail metadata/content and connection status, while agent_events:read maps only to agent events. No write, send, draft, archive, delete, or relabel capability is defined.

Each implementation must define focused input/output Zod schemas, bounded pagination/excerpts, stable errors, and annotations readOnlyHint: true, destructiveHint: false, openWorldHint: false.

OAuth/MCP protocol requirements

  • Publish protected-resource metadata and authorization-server/OIDC discovery. Echo the exact resource through authorization and token exchange.
  • Use authorization code + PKCE S256. Support the selected OpenAI client-registration path (CIMD, DCR, or predefined client) and allowlist the exact redirect URI.
  • Validate signature, issuer, exact audience/resource, subject-to-Orca-user mapping, issued/expiry times, explicit account allowlist, scopes, and revocation before every tool read.
  • Return 401 with a standards-compliant WWW-Authenticate challenge and protected-resource metadata link for missing/invalid authorization; use 403 for valid tokens missing a required scope/account.
  • Authorize the source deep link using the same user/account context. A URL is never evidence of access.

Current basis: official OpenAI documentation for plugin MCP authentication and building MCP servers. The official guidance requires OAuth 2.1 for authenticated MCP, protected-resource metadata, PKCE S256, explicit schemas, accurate safety annotations, and authorization in each handler.

Feature gates

  • ORCA_M6_PROPAGATION_ENABLED=false
  • ORCA_M6_MCP_ENABLED=false

Both flags default off and are independent. Turning on one does not turn on the other, configure a model, or grant provider write access.

Storage handoff

BRE-263/264 should add an account-owned agent_events table matching the shared schema. Minimum indexed fields:

id, owner_user_id, account_id, message_id, thread_id, event_kind, deduplication_key, state, revision, created_at, updated_at.

Unique: (owner_user_id, account_id, deduplication_key). Foreign keys cascade with the local account/source. No backfill is required; feature enablement evaluates newly ingested mail only unless a separately bounded backfill is approved.

Backward-compatibility line

M6 does not add required fields to existing inbox, thread, account, auth-session, Human Signal, or attention responses. Existing routes do not evaluate, persist, or return agent events while the flags are off. New storage and routes are additive. Old databases require no agent backfill to start. Unknown future enum values require a versioned contract change—not silent client reinterpretation.
