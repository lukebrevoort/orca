Three memory fixes implemented

Local changes only. Production remains stopped. No deployment, push, Railway configuration change, or production database migration was performed. Memory limits and Serverless settings remain outside this patch.

What changed

FixBehavior and evidence
Classification lookupNew migration 0039_classifier_lookup_index.sql adds an account/version/time/ID covering index. The account-wide stale-version check selects IDs only, then loads evidence for at most limit+1 IDs (maximum 501). Fully current accounts load no evidence. Regression tests inspect the actual query plan, preserve null/current/old version behavior, and exercise deletion, reparenting, and concurrent refresh protection.
Thread-detail projectionMessage bodies are fetched once. Labels and attachment metadata use separate narrow queries. An HTTP regression checks the complete response, account isolation, and materialized SQL body bytes; MCP coverage checks fanout and redaction. In its fixture, fetched body bytes fell from 1,048,632 to 524,316 with the same required message content.
Bounded Gmail history syncLightweight metadata establishes global normalized date/ID order before full bodies are fetched. Metadata requests use at most five concurrent calls; full-body fetches are serial. Persistence batches target 25 messages or 4 MiB of serialized provider payload. Deletions use 25-ID chunks. Whole-drain counts remain distinct, and the history cursor advances only after complete success.

  • Classification: covering-index zero-work lookup, bounded evidence hydration, deterministic limits/order, compare-and-swap protection, fresh and upgrade/reapply migration paths.
  • Reader: multiple messages, labels and attachments; body data fetched once; unchanged HTTP/MCP shape, sanitization/redaction, and account isolation.
  • History: out-of-order pages, timestamp ties and missing/ISO dates, chronological live-rule evaluation, count and byte flushes, aggregate counts, provider failures, lease loss, metadata/body changes, add/delete reconciliation, 404s, partial failure and idempotent replay.

Measured diagnostic result

The same synthetic 250-message × 100 KB plain-text history fixture completed after the changes with RSS approximately 125.4 → 202.1 MiB. The earlier run was approximately 125 → 284 MiB. Before the final synthetic ID's body fetch, 150 messages were already saved, versus zero before the fix. All 250 messages were ultimately persisted.

These are separate Bun 1.3.14/macOS runs with mocked Gmail, not a Linux container memory ceiling or a production cost forecast. The fixture exercises the compatibility path for a client without the new optional metadata method. Raw evidence is stored beside this report in history-comparison.json and history-after.jsonl.

Tradeoffs and limits

  • The 4 MiB target bounds retained batch input, not process RSS. One incoming oversized message, normalization copies and runtime memory can exceed it. Compact ID/order/counter sets still grow with the amount of history.
  • Ordering adds a metadata request per changed message. Serial body fetching trades catch-up speed for predictable retained payload. Older custom clients without the metadata method use a serial full-message fallback to obtain ordering keys, then fetch bodies again for persistence.
  • The classifier still scans a compact index to identify outdated versions. Broader Organization snapshots and inbox count scans are unchanged by this requested patch.
  • These fixes do not prove the composition of the former 2.3 GB production footprint. Linux application/file-cache profiling and a measured memory limit remain necessary before promising a $5 monthly budget.
  • The migration is additive; the new index needs disk space and build time when applied. Production has not run it.
