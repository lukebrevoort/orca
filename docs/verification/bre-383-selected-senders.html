Use selected message senders

A focused review guide for the authoritative row-selection handoff, the shared View authoring path, and return behavior.

Contract at a glance

1 · Selectvisible message rows
2 · PrepareIDs only
3 · Resolvestored exact From
4 · Saveaccount + senders
Client sends{accountId, threadId, messageId} for every selected visible row. It never sends a sender address as authority.
Server provesEvery reference is workspace-owned and internally consistent in one transaction. Any unavailable reference fails the preparation.
Server derivesThe exact stored from_address, excluding only normalized provider_email self rows, then deduplicating.
View persistsOne accountIds value plus a positive sender allowlist. Selected Thread or message IDs are never persisted.

Five-minute manual review

Visual evidence only. The /dev/inbox demo and its screenshots prove layout, stacking, focus, controls, and theme behavior. Its demoPreparationResponse uses fixture senders, so it is not persistence evidence. Use the production scratch-database proof below for authoritative sender resolution and saved-result behavior.

  1. Run bun run dev, then open the demo Inbox.
  2. Choose Select, pick one or more rows, then choose Use these senders. To inspect the self-omission notice visually, use self-omission evidence; this remains visual-only fixture state.
  3. Confirm the builder shows one exact account and the normalized sender addresses. Edit them, preview, and save through the existing shared View flow.
  4. Open the builder again, scroll the list first, then choose Cancel or press Escape. The same rows, scroll position, and Use these senders focus return.
  5. Open mixed-account evidence, select rows from both accounts, and confirm preparation stays disabled with explicit copy while the selection remains.
  6. Switch between Light and Orca Black. Check default, hover, focus, selected, and disabled controls at 1440×900 and 1024×768.

Runnable production scratch-database proof

This command runs the real migrated SQLite repository, Hono routes, shared request/response schemas, and commit path against a disposable database. No demo preparation helper participates.

# Run from the repository root.
bun test apps/api/src/organization/views/verification.test.ts \
  --test-name-pattern "prepares exact selected-message From"
Validated triplesaccount_a/thread_a/message_maya and account_a/thread_b/message_maya_duplicate remain two distinct authoritative references through the repository join, even though both resolve to Maya. A separate self triple proves the omission notice. The first stored From is wrapped at both edges by every character JavaScript trim() accepts.
Exact prepared resultThe response is asserted as accountIds:["account_a"] plus sender.addresses:["maya@example.com"]. The duplicate external address is deduplicated only after validation; the self row produces a typed omission notice.
Preview and saveThe unsaved preview must include both selected Threads plus thread_unselected_sender, an existing matching Thread never included in the preparation. Commit receives the same reviewed definition; no selected IDs are persisted.
Reload and future mailAfter commit, the proof inserts a new Thread whose mixed-case From has the same full whitespace wrapper, reloads saved results through the production route, and asserts that future Thread matches. The same SQL edge-trim expression is exercised for exact-address and domain Views.

The exact trim set is U+0009–U+000D, U+0020, U+00A0, U+1680, U+2000–U+200A, U+2028, U+2029, U+202F, U+205F, U+3000, and U+FEFF. SQLite trims only those characters from the edges—internal whitespace is not removed—then lowercases for preparation and sender address/domain evaluation. The test also proves pure-external selection has no omission notice, mixed external+self does, all-self fails recoverably, a malformed stored From fails the whole request even when it equals a malformed provider email, mixed-account fails whole-request, and foreign/mismatched references cannot narrow silently. The temporary database is removed after the run.

Automated evidence

  • Shared: strict bounded references, duplicate rejection, and no client-enriched From field.
  • API/repository: single/multiple senders, normalized duplicate From, self/all-self, mixed account, bad/foreign references, dynamic existing and future mail, commit and reload.
  • Web: IDs-only handoff, missing-selection disablement, mixed-account block, retained row selection, scroll/focus return, generic typed prepare entry, prepared update identity, complete advanced-predicate preservation, unsupported-clause remove and Undo. A schema-canonical semantic preparation identity synchronously hides an old draft and disables commit when a replacement entry is pending; delayed failure, delayed success, stale prepare/commit responses, duplicate submit, and Cmd/Ctrl+Enter are covered without crossing return contexts.
  • Browser: real pointer clicks reached the name input, filter menu, Cancel, Save, and backdrop return control; heading-first focus and return focus passed. Light and Orca Black at 1440×900 and 1024×768 each reported zero axe WCAG A/AA violations or incomplete checks.
