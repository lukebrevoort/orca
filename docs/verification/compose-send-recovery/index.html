Compose and send recovery

Candidate based on main 6b813bd0. All mail data and deliveries used for automated verification are synthetic.

Fixed paths

  • Web draft reads, saves, conflict copies, discard, status polling, and send explicitly retain the composed account. A regression test against the original composer delivered through the first account instead of the second; the fixed composer uses the intended account.
  • Gmail preparation failures before sendMessage are confirmed-unsent rejections. Existing explicit edit-copy recovery can proceed. Post-dispatch unknown outcomes stay ambiguous and cannot silently send again.
  • Late draft mirroring cannot replace sent message/thread IDs or overwrite a reserved delivery record.
  • iOS refreshes sending capabilities on foreground and composer entry and offers a refresh action after web consent. Refresh failures preserve writing and account identity.
  • iOS can inspect a server-origin delivery without a local idempotency key. It uses GET rather than creating another send command.
  • iOS limits attachments to 25 and permits removing a file before sending.

Automated verification

The added web integration runs the production composer and draft controller, real Hono routes and SQLite persistence, and an injected provider transport. It covers pending To/Cc/Bcc, multiline body, autosave, double-click send, invalid recipient retention, and uncertain-delivery replay. It is Happy DOM component/API integration, not a browser or native UI end-to-end pass.

Review and current limits

An independent reviewer reproduced all 14 added executable regressions and both same-process fixture checks. Review found a Keep both/attachment-removal race; the revision now uses one exclusive operation reservation and drains initialization/autosaves before reconciliation or delivery. Additional native concurrency regressions are written but require Xcode. Keep both also checkpoints the newest visible writing before the remote verification, retaining it if that request stalls or fails.

Typecheck, lint, and production build passed. The full suite is not consistently green: the existing Reader retry-count failure also reproduces on unchanged main. MCP and attention checks showed intermittent parallel-run failures; focused rechecks passed. Exact final run counts and revision accompany the patch.

Required native UI verification

Not yet executed: Xcode build, native unit tests, iOS simulator flows, physical-device behavior, and real Google consent/provider delivery. Linux has no Xcode. The managed browser rejects the loopback fixture, and shell Chromium cannot create its local socket. No screenshot or full UI end-to-end pass is claimed. Do not release this candidate before native verification.

Remaining scope

  • Gmail sending consent still uses the web. A native in-app permission upgrade needs a deliberate mobile/browser OAuth bridge; directly redirecting the bearer-bound OAuth transaction would fail the session-binding protection.
  • Provider 429/403 classification and richer delivery error persistence remain follow-up work.
  • Successful messages.send does not consume the mirrored Gmail draft; provider-draft cleanup and recreating externally deleted draft copies remain separate provider integration work.
  • No real email was sent, no credentials changed, and nothing was pushed, merged, deployed, or released.
