## Contract for the next client/notification stages

All endpoints require the existing cookie/mobile session and current ownership of the explicit account. All responses are private/no-store. Mutations accept JSON only and a bounded body. No provider or notification permission is required to make a local choice.

- `GET /v1/importance/conversations/:threadId?accountId=…`: current effective result, direct choice/revision, inherited result, counts of distinct inbound exact-address participants, actual explicit contributing preferences/revisions and account revision. Removing a conversation choice inherits this **current** result; it does not promise Unreviewed. Preferences are ordered Important first/address and capped at 20 with `preferencesTruncated`; counts cover all participants.
- `GET /v1/importance/senders?accountId=…&address=…`: current exact-address choice/revision. Known inbound addresses or retained preference tombstones only; arbitrary unseen targets return 404.
- `POST /v1/importance/choices`: `{accountId,target:{kind:"conversation",threadId},choice:"important"|"not_important"|null,expectedRevision,operationId}`. `operationId` is a fresh UUID per intended command, stable across retries. Initial revision is 0. Every acknowledged change, including a no-op/reset, increments the target revision; null is a retained tombstone. Sender targets instead use `{kind:"sender",address}` and require `confirmation` from a current preview.
- `POST /v1/importance/preview`: `{accountId,address,choice}`. No writes. Returns exact counts of matching existing conversations, preserved overrides, before/after effective counts, actual changed conversations, and conversations kept Important by other participants. The future contract explicitly names the account/address, preserves conversation overrides and warns that other Important participants can keep the conversation Important. It never predicts a count of future mail. The opaque confirmation is account/user/address/choice/revision scoped and expires after five minutes. Any account-mailbox revision change requires a new preview before sender commitment.
- `GET /v1/importance/operations/:operationId?accountId=…`: reconcile a dropped/ambiguous response. Returns the original receipt **and current choice**. `status:"superseded"` means a newer revision exists; never render the receipt's old choice as the current one. A 404 after a fresh authorized reconciliation means this account has no committed operation; retrying the exact original command is safe because the revision guard still applies. Offline/unauthorized reconciliation establishes nothing.
- `POST /v1/importance/operations/:operationId/undo`: `{accountId,operationId:<new UUID>,expectedRevision:<receipt.revision>}`. Available for five minutes after the server commits the mutation. Restores only that receipt's previous explicit choice if the target is still at the exact receipt revision; Undo itself advances revision and has its own idempotent operation. If previous choice was null, inheritance uses current preferences/participants. Broader sender Undo restores the exact sender target, affecting its current matching/future conversations while preserving current overrides. It is not global persisted user history. Receipt storage supports reconciliation; the UI affordance is transient.
- `GET /v1/important?accountId=…&limit=1..100&cursor=…`: retained conversations whose effective result is Important. Uses retained local mail, independent of destination/INBOX labels. No provider move or permission change. Stable ordering: newest message received time, then thread ID; null times sort as epoch. Opaque cursors bind user/account/page-size/account-revision. Stale, altered or cross-scope cursors return 400; restart from the first page. Send no cursor after changing account/page size. Clients must also keep their existing request-generation guard: an old account's successful response may never install in a new account.

For existing endpoints, clients explicitly request `x-orca-importance-version: 1`. Legacy requests keep their exact response shape: old web clients use strict Zod decoders and cannot accept an unrequested field. Mailbox `/v1/inbox` rows and `/v1/threads/:threadId` plus recovery-page responses add optional `importance` projections. Existing request shapes and legacy attention/classification/placement fields remain valid. Important uses the **same** resolver/projection as these reads. `readImportance` is the batched API-side integration point for BRE-455: consume `effective === "important"`; do not infer eligibility from HumanSignal, unread state, destination, or a receipt. This stage deliberately does not enable notification policy or delivery.

## Resolution and persistence

An explicit conversation choice wins. Otherwise aggregate **all distinct inbound exact addresses** within that account: any Important → Important; otherwise any Unreviewed → Unreviewed; otherwise all Not important → Not important; empty → Unreviewed. No latest-sender fallback. Addresses normalize trim/ASCII case consistently with existing exact-address contracts; no domain, plus-alias or cross-account expansion.

Inbound uses persisted metadata: a nonempty sender other than the account's exact provider address, not a draft and not linked to that account's provider SENT/DRAFT label. This is not an AI authorship heuristic. The existing mail model has no explicit provider direction/alias catalog; an unlabelled outbound message from an unknown alias cannot be identified as outbound. No aliases are invented. Provider SENT labels handle known sent aliases. Unknown/empty senders contribute no exact-address preference and empty sets remain Unreviewed.

Migration 0052 backfills distinct participants and an indexed effective state from retained mail. Triggers maintain it on message insert/delete/sender/draft/time edits, label association/catalog edits, account address changes and explicit choices. Body/read edits do not recompute participants. Reads join/batch this metadata; Important lists never select bodies. The partial page index excludes zero-retention threads. Sender choices deliberately pay update work for matching conversations so list selection can use the effective index. Preference provenance enrichment visits participants for only returned conversations; its work scales with those participant sets (the 20-result cap is not a claim of 20 SQL work units). Migration/backfill and unusually long conversations require proportional write work; there is no constant-time claim.

Choice tombstones and operation receipts remain until account/user deletion, including conversation deletion/recreation with the same local ID. Deletion advances a null conversation tombstone even when no previous choice existed; a recreated local ID cannot accept an old initial write or Undo. A rollback must preserve these revisions; deleting tombstones admits ABA stale commands. No endpoint deletes/reset-recreates a revision root. Existing provider/thread identifiers are account scoped; the three-account test uses the same provider thread reference and exact sender under two users.

## Reproduce

Use existing frozen-lockfile dependencies, Bun 1.3.14, Python 3 and the checkout's normal TypeScript toolchain. No server, browser, credentials or simulator is needed for this scoped fixture. Resource coordination uses the parent's temporary cooperative wrapper when available:

```sh
python3 /tmp/orca-ui-heavy-slot.py bun test apps/api/src/importance/routes.test.ts packages/shared/src/importance.test.ts
python3 /tmp/orca-ui-heavy-slot.py bun apps/api/scripts/importance-fixture.ts /tmp/bre454-evidence-NEW
```

The fixture refuses an existing output directory, uses a new owned temporary SQLite file, authenticates synthetic sessions, writes through the actual API, independently reopens SQLite, reads authorized mailbox/Important projections, compares unchanged mail/placement, and fails on any provider call. `demo.json` records eight actual assertions, not a UI simulation.

The query harness captures every actual read statement/binding and returned-row count for first/next 50-conversation pages on 1,000/5,000 conversations (5,000/25,000 messages; two distinct inbound participants per conversation). Independent Python SQLite replays those statements against the same frozen fixture, counts progress callbacks at interval one as a deterministic proxy for VM work, verifies returned counts and records index plans. A separate in-memory backup measures a broad sender update including trigger work. Engine versions are recorded; these are actual query counts and measured progress-callback work units on that engine, not Bun latency or speedup measurements. No baseline timing comparison is meaningful because the baseline has no importance route.

Run full workspace lint/typecheck/tests/build sequentially at the committed final head. The parent later repeats on the combined revision. Compose/browser/native journeys are separate hosted gates; no UI/native success is claimed by these API tests. The verify-orca doctor initially found Node 26. The existing cached Node 24.22.1 was then located and used; doctor still reports no provisioned Playwright Chromium without an explicit executable. No browser install was attempted. This does not block the Bun-only API fixture and is not a successful compose/native trial.
