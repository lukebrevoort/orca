A native iPhone mail client for reading comfortably, writing without friction, and receiving useful notifications. Initial release serves Luke's existing Orca account. Implementation is authorized and underway; this brief records the intended scope, not a completed validation report.

What exists today

Reusable server capabilities

The repository already implements provider login, inbox and thread APIs, revisioned drafts, real sending, Gmail push ingestion, and Outlook connection scaffolding. Outlook sync and delivery remain unimplemented in its provider adapter. The root agent manual understates these capabilities. Authentication currently reads an HTTP session cookie.

Development environment

Xcode 26.4.1 and a booted iPhone 17 simulator are available. No existing Swift or iOS project was found. Deployment configuration points the web API proxy at Railway; the user's active deployment remains to be confirmed.

First-release priorities

  1. P0 · Read: human-first inbox, full conversations, search, attachments, explicit unread state, and useful cached content when connectivity drops.
  2. P0 · Write: compose, reply, reply all, forward, recipient entry, attachments, durable drafts, and explicit delivery outcomes. A failed or ambiguous send must never silently duplicate a message.
  3. P0 · Notify: authenticated device registration and server-to-APNs delivery; tapping a notification opens its conversation. Default is Inbox, with independent opt-in selection of individual Spaces. Human Signal does not gate alerts.
  4. P0 · Connect: secure sign-in to the existing account, provider permission upgrades for sending, session expiry recovery, and clean sign-out.
  5. P1 · Organize: established mailbox actions and existing organization results. Complex rule authoring stays outside the initial mobile scope.

People and situations

Daily reader and writer: Luke handles correspondence between meetings, reads on the move, and writes longer replies when needed. Accessibility includes large text, VoiceOver, light/dark appearance, and comfortable one-handed operation.

Release operator: Luke or the project maintainer provisions the signed app, API deployment, and push credentials. The release must distinguish simulator validation from a verified installation on the actual phone.

Proposed direction

SwiftUI for the app, with Apple's system authentication session and existing Orca APIs. Preserve Orca's calm visual character and recognizable contacts. Favor readable typography, restrained color, familiar native interactions, and clear delivery state.

Principles that settle trade-offs

  • Never lose words. Draft durability precedes animation or editor embellishment.
  • Interrupt deliberately. Notification eligibility follows the user's attention policy; initial sync must not generate a flood of old-mail alerts.
  • Tell the truth about state. Distinguish cached content, saved drafts, sending, confirmed delivery, and uncertain delivery.
  • Give reading room. Keep desktop administration out of the central reading and writing experience.
  • Protect the mailbox. Keep credentials in platform-secure storage and message content out of diagnostic logs and default push payloads.

Engineering challenges

  • Bridge browser-based provider login to a separately authenticated native client without exposing reusable credentials in callback URLs.
  • Connect provider ingestion to durable, deduplicated Apple push delivery. Existing Gmail push sync does not itself notify an iPhone.
  • Reconcile drafts across devices, interrupted saves, and uncertain send outcomes.
  • Render real HTML email and attachments while controlling external content and navigation.
  • Verify launch, login, reading, writing, notification taps, offline recovery, and both themes on simulator and device.
