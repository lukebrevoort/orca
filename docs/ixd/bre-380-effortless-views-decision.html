01

One authoring journey

The source differs; every step after preparation is shared. Create and Edit use the same layout and definition controls.

  1. 01 · StartSearch or select

    Search shows mail first. Selection exposes “Use these senders.” Neither asks for a View name.

  2. 02 · PrepareTyped draft

    The server validates scope and translates exact clauses or resolves selected row identities.

  3. 03 · PreviewMatching conversations

    Readable definition, result-count state, pagination, provenance, and unsupported clauses stay visible.

  4. 04 · RefineTune or correct

    BRE-378 controls edit the draft. Latest-request ordering prevents stale previews from winning.

  5. 05 · ReviewName and save

    A suggested name is editable. Save persists the reviewed definition, never result IDs.

  6. 06 · ResumeOpen the live View

    The new View opens under My spaces. Back restores the exact search or selection context.

Search entry

  1. Open Search with ⌘K; type or set visible filters.
  2. Results render in the normal central mail list.
  3. “Keep as View” appears only after a search has run. Unsupported clauses remain visible and block Save, not preview.
  4. Activate “Keep as View” to enter the shared draft workspace without losing the search URL or result position.

Selected-row entry

  1. Select one or more message/conversation rows from one connected account and activate “Use these senders.”
  2. The server resolves only the From identity visibly represented by each selected row from authorized account/thread/message references.
  3. The shared workspace opens with that account and its exact address allowlist plus preview results.
  4. No selected thread ID becomes live membership; no hidden participant, historical correspondent, topic, or subject restriction is inferred.

Create, edit, save, discard

Create and Edit share one draft representation and one evaluator. Edit seeds that draft from the complete saved definition, including advanced filters the compact controls do not modify. Cancel leaves the saved View untouched. Save rechecks workspace authority and expected revisions, is retry-safe, and changes no mail placement, provider state, notification, or routing policy. A save failure preserves the draft and names the next safe action. Discard affects only the local draft.

A valid zero-match View may be saved for future mail—with explicit confirmation.

A blank draft, a draft containing only no-op scope, or a draft with any incomplete or unsupported clause is invalid: Save stays disabled and the first invalid control receives focus. When the shared View evaluator successfully returns zero current conversations for a complete, supported definition, show “No conversations match this View yet. Future matching mail will appear here.” Keep Review filters and Save for future mail available. The first Save action enters the existing confirm-zero state and says “This exact scope currently has zero matches. Saving it will keep watching for future mail.” Only a second, explicit Save zero-match View action commits. Canceling that confirmation preserves the entire draft, source query, and return snapshot, then restores focus to Save; Review filters focuses the first predicate without changing it. After confirmed Save, open the canonical empty View under My spaces with the same zero-result copy. A preview error is not a zero-match result and never permits blind Save.

03

Durable navigation

Saved Views are work destinations, not artifacts hidden inside the Organization editor.

Open saved Views from My spaces.

Each saved View is projected into the BRE-321 My spaces section and opens through a stable destination keyed by View ID (recommended location form: /?destination=view:<viewId>). Organization → Views remains the management index for create, rename, reorder, remove, and advanced editing.

After Save

Replace the authoring location with the canonical saved-View destination, focus its heading, announce “View saved,” and keep the originating source in surface history.

After reload or on another device

Load the server-owned View list before resolving the destination. Restore the same View by stable ID; never rely on in-memory state, display name, or local order.

If the View is missing, removed, or unauthorized

Open Organization → Views with an operational message naming what happened. Do not silently fall back to Inbox or another View.

Rename, reorder, remove

Rename preserves destination identity. Server order drives My spaces. Remove deletes only the View; mail stays unchanged and focus moves to the next View or the Organization → Views heading.

Risk and fallback

Risk: Collections and saved Views may both appear as custom spaces. Fallback: render a single My spaces list with a small type affordance only in Manage spaces; do not create separate global navigation sections. If route projection is not ready when persistence lands, Organization → Views is the temporary retrieval surface—but M9 is not complete until reload retrieval from My spaces works.

04

Sender identity

Each selected row contributes only the exact sender identity the row visibly represents. Hidden conversation history is never mined for additional people.

Identity key: one account ID + normalized visible-row From address.

The selection handoff contains stable { accountId, threadId, messageId } row references—not client-asserted email addresses. messageId is the internal InboxMessage.id, never the provider message ID. A regular inbox conversation row is backed by the latest message selected by getLatestThreadRows; a global Search row is an individual message. In both cases, the server validates every triple, resolves and normalizes only that stored row’s emails.from_address, and then deduplicates addresses for the one-account View definition. The response displays the authoritative exact address for confirmation. A selected row contributes no other participant or earlier correspondent.

M9 single-account and selection-state constraints

The current View definition can exactly represent accountIds: [oneAccount] plus a positive sender set. With multiple accounts it creates an account × address cross-product, which is broader than the selection. Therefore M9 enables “Use these senders” only when every selected row belongs to one connected account. The client must retain separate row selection keyed by [accountId, messageId] with threadId; the current sender-deduped selectedTargets projection is display/provenance only and is not authoritative input. Account-scoped sender groups are a possible later extension, not an implicit BRE-381 requirement.

Predicate conjunction is narrower than “any message” independently

Sender, date, and classification/evidence clauses are combined inside one EXISTS emails e: the same stored message must satisfy every email-level clause. Thread subject/read and Lane constraints then combine with that result using AND. The readable definition and preview tests must state this grouping.

Unsupported-clause rule

If any clause is unsupported, preview may continue using the source Search semantics, but Save remains disabled. Every unsupported clause stays in the readable definition with a reason and two explicit actions: Edit/replace it or Remove it. Removing or replacing a clause is a visible meaning change followed by a new View preview. There is no “Save supported parts,” no silent dropping, and no subject-only fallback.

Count and pagination truth

Current View result pages expose items and nextCursor, not an exact total. Display “25 loaded · more matches” until the evaluator computes an exact count for the same authorized scope and definition digest. An exact label such as “18 matching conversations” is permitted only when that exact count is returned; never infer a total from one page.

Evaluator risk and fallback

Risk: current global Search returns message rows while Views return conversation aggregates. Even identically named filters can diverge. Fallback: once “Keep as View” begins, run the shared unsaved View evaluator and label the transition “Previewing conversations for this View.” BRE-387 must prove saved/unsaved equivalence across pages, accounts, and future mail before release.

06

Correction and undo

M9 supports deterministic positive narrowing. It does not claim “exclude this result” or semantic correction.

Draft scope

  • Every correction changes only the open draft until Save.
  • The preview request carries a definition digest; late responses with another digest cannot replace the current result.
  • Save persists the reviewed definition, not preview membership.
  • Cancel Edit restores the saved View exactly, including advanced constraints.

Undo scope

  • Undo reverses the latest definition-changing action: add/remove/edit filter, sender selection, or quick correction.
  • It does not undo ordinary typing inside the focused name/description field; native text undo remains local there.
  • The stack is session-local, bounded, and cleared on Save or confirmed Discard.
  • After Undo, preview reruns and focus returns to the changed control; a live region announces the restored summary.

Wrong match → “Keep only these senders”

  1. The quick action never means “exclude this sender.” It opens a positive allowlist editor.
  2. Offer it only when the draft’s effective scope is exactly one account. Candidates come from a server-reported complete distinct-sender summary for the current preview scope, not from the visible page.
  3. If one-account scope or complete candidates cannot be proved within the contract bound, the quick action is unavailable and Tune opens instead.
  4. The wrong result’s sender starts unchecked; every remaining checked address is visible with the account.
  5. Before Apply, state the consequence: “Future mail matches only these addresses. New senders will not appear until you add them.”
  6. Apply creates/replaces the positive sender allowlist and reruns preview. Undo restores the exact prior definition.

Empty-set invariant

Zero checked senders is invalid. Disable Apply and show “Keep at least one sender, or cancel this correction.” Never serialize []; never remove the sender predicate as an interpretation of an empty allowlist, because omission means all senders. If removing the wrong sender leaves no positive sender, offer Tune or adjust the subject/date/read filters.

Deferred: true exclusion

No M9 control is labeled “Exclude,” “Never show,” or equivalent. A true negative predicate would require bounded account-aware schema, evaluator, cursor-digest, readability, and migration work. It may be proposed separately; it is not promised by BRE-380.

07

Onboarding scope

Teach one next action. Persist dismissal for the Orca user, not per browser or per connected provider account.

User-scoped dismissal, durable across reload and devices.

Add a nullable first-View invitation dismissal/completion timestamp through the existing authenticated user-preferences mechanism. Once dismissed or once a first View is saved, the invitation stays hidden for that Orca user across reload, sign-in on another device, and adding/switching connected mail accounts. A different Orca user sees their own invitation. Organization → Views → “Getting started” always reopens it without clearing the stored preference or duplicating Views.

Mailbox with mail

Offer exactly two actions: Search mail and Select conversations. Each enters the same production journey described above. No automatic View, notification permission, filter taxonomy tour, assistant toggle, or agent setup.

Empty mailbox

Show a clearly labeled, non-interactive sample explaining the outcome, plus Skip for now and Return when mail arrives. The person can reopen help later. Do not manufacture a savable production draft.

Fixture isolation

Tutorial fixtures live outside the real mailbox repository and carry a non-committable tutorial provenance. They never use production account IDs, thread IDs, message IDs, or sender addresses. The commit interface rejects tutorial provenance. A real action always restarts through prepare with authorized stored-mail references; sample sender/account identifiers can never persist as a View.

09

Human usability threshold

This is a proposal for owner approval, not existing evidence and not yet a release gate.

Owner approval pending

Proposed: 4 of 5 uncoached participants succeed.

A participant succeeds only if they independently (a) start from Search or selected conversations, (b) preview and save a useful View within 60 seconds, and (c) correct one deliberately planted wrong match without assistance. Time starts when the task prompt ends and stops when the saved View opens under My spaces. The correction may occur before Save in the same 60-second attempt.

Report separatelyComprehension

Unsupported-clause confusion, sender/account scope understanding, and whether positive narrowing is mistaken for exclusion.

Report separatelySystem latency

Prepare, first preview, correction preview, and Save duration. Do not count network delay as interaction confusion.

Do not claimEvidence before sessions

Prototype exercise and automated checks prove operability, not uncoached human usability.

Fallback if the owner rejects the threshold

BRE-387 records the revised sample, time box, success definition, and permitted coaching before sessions begin. Engineering verification can continue independently, but M9 remains open until the owner-approved human protocol is run and reported.

10

Contract handoff

One deep Views module owns translation, identity, preview equivalence, authority, and commit. Callers do not recreate those decisions.

Deepen the existing Views module at its current seam.

The interface below gives Search, selected-conversation entry, onboarding, Create, and Edit one small surface. The implementation hides clause translation, visible-row identity resolution, definition digests, pagination, authorization, revisions, and retry semantics. The SQLite adapter satisfies the repository seam. Tests exercise the same interface as production callers.

prepare(scope, seed) → ReviewedDraft
  seed = SearchSeed | SelectedConversationSeed | SavedViewSeed

preview(scope, reviewedDraft, page?) → {
  validatedDefinition,
  readableSummary,
  effectiveAccountScope,
  unsupportedClauses,
  results,
  resultCompleteness,
  definitionDigest,
  provenance
}

commit(scope, reviewedDraft, expectedRevisions, retryKey) → SavedView

Invariants behind the interface

  • Unsaved and saved definitions use one evaluator.
  • Draft preview never persists a temporary View.
  • Cursors bind to definition digest and authorized scope.
  • Account/thread ownership is resolved server-side.
  • Latest preview wins; failed work preserves input.
  • Confirm-zero is bound to the current definition digest and clears after any definition change.
  • Commit rechecks live authority and revisions.

Explicit non-goals

  • Natural-language intent or conversational refinement.
  • Topic, person, or similarity inference.
  • Railway/local-model/runtime decisions.
  • True sender/thread exclusion.
  • Notification or routing changes.
  • BRE-381 implementation in this artifact.

Risks and bounded fallbacks

Search mismatch
Block Save for unsupported clauses; never weaken the query.
Mixed-account selection
Require one account in M9; do not broaden through a global sender set.
Incomplete sender census
Hide quick positive narrowing and open Tune; never derive from one page.
Blank or incomplete draft

Valid zero matches

Missing return target
