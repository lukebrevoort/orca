Two ways to start

Search mail

Type a search, see matches, then save. The prototype explicitly searches subject text. Production must preserve the exact supported search filters.

Use selected senders

Select messages and create a view from their senders. The same senders' other messages can appear. No inferred topic or similarity score.

Refine directly

Unread only, subject and sender controls update a readable definition. Preview a correction and undo it before saving.

Compare three layouts

A: Search first starts with a search and its results. B: Workbench keeps controls next to the results. C: Beside mail keeps an inbox beside a drawer. Use the floating arrows to compare. No winner is selected yet.

Try the revision

  1. Search for apartment: four subject matches appear. Preview this view.
  2. Correct the furniture match: keep the other matching senders. Three results remain. The explanation warns that new senders are also excluded. Undo restores the prior draft.
  3. Save, rename, reorder or remove a view. Mail remains unchanged.
  4. Start again with selected mail: two messages from Maya and Juniper produce three matching conversations.
  5. Open Edit filters; change subject, sender or unread state. An empty view can be saved for future mail.

No topic inference: searching apartment is not equivalent to understanding apartment hunting. Readable controls can provide low friction without pretending to understand unrestricted requests.

Deep module proposal

prepare(scope, searchOrSenderSelection) → typed draft
preview(scope, definition, page?) → matches + digest + provenance
commit(scope, reviewedDraft, expectedRevisions, retryKey) → saved view

Extend the existing Views module and share the same evaluator for unsaved/saved queries. Current BRE-378 previews a definition but runs matching only after Save; that is the main missing capability. Keep permission, account scope, revision and retry checks behind the existing interface. Drafts remain local until commit.

Search translation must be exact. The current View contract supports subject substring and positive sender sets, not unrestricted semantic search or general exclusions. Keeping other known senders is a visible narrowing operation; true thread/sender exclusion requires a reviewed contract extension.

There is no model adapter in M9. Later assistance can emit the same typed draft after it is validated and benchmarked.

Seven implementation tickets

BRE-380 · Design effortless views from search or selected senders

Compare A: Search first, B: Workbench, C: Beside mail. Preserve the existing Orca shell and BRE-378 progressive controls. The first action is searching or selecting mail, not naming a view or configuring attention.

- Search results appear before saving; the interpretation names exact supported filters.
- Selected mail offers “Use these senders,” with explicit sender-set semantics. No topic inference or “more like this” promise.
- Specify preview, rename, manual refinement, correction/undo, save, discard, return context, and empty/error states.
- Resolve correction scope, supported search translation and keyboard/focus behavior. Preserve theme-safe controls in Light/Orca Black.
- Review the HTML study with the owner and set an uncoached usability threshold; proposed 4/5 participants create a useful view in 60 seconds and correct a match.
- Read docs/ixd/bre-321-ui-switch-spec.html; retain shell and authority requirements.

AI description and conversational refinement are deferred to BRE-382 outside M9.

BRE-381 · Unify view drafts, matching-mail preview, and explicit save

Own packages/shared/src/organization-views.ts, apps/api/src/organization/views/{module,routes,sqlite-repository}.ts, and shared web draft orchestration.

Deep module interface: prepare(scope, searchOrSenderSelection), preview(scope, definition, page?), commit(scope, reviewedDraft, expectedRevisions, retryKey). No interpreter/model adapter is required for M9.

- Add a read-only unsaved definition preview (proposed POST /v1/organization/views/preview). Reuse the saved-view query evaluator, not a second matching implementation.
- Return validated definition, readable summary, effective account scope, result provenance and definition digest. Bind cursors to digest and authorized scope.
- Preview never creates a temporary persisted view. Discard is local.
- Save delegates to existing create/update, rechecks live authority/revisions, and is retry-safe. Mail may change between preview and save; persist the reviewed definition.
- Preserve advanced filters, input on failure, and latest-request ordering. Creating a view changes no mail placement, provider state, or notifications.

Validate at the interface: saved/unsaved query equivalence, account isolation, cursor binding, stale responses, revoked permission, retry deduplication and no preview mutations.

BRE-383 · Create a view from the senders of selected mail

Own inbox/reader selection handoff and deterministic sender-set preparation through BRE-381. This no longer depends on BRE-382.

- Select one or more messages and choose “Use these senders.”
- Pass account/thread references and resolve sender identity under authorized scope; do not trust client-supplied ownership.
- Populate a sender-set query and preview matches beyond the selected messages, including future mail from those senders.
- Show the exact sender names/addresses and let the user edit the set. Do not infer topics or silently add subject restrictions.
- Preserve list position/selection on cancel; handle missing threads and mixed accounts truthfully.
- Never store selected IDs as static live-view membership.

Validate one/multiple senders, mixed-account authorization, other matching threads, save/reload and cancel-return. Provide keyboard and both-theme screenshots.

BRE-384 · Save a useful mail search as a live view

Own search entry in global-search.tsx, exact search-to-view translation, and BRE-381 handoff.

- Search using explicit words and visible sender/date/unread/account filters; preview matching mail and suggest an editable name.
- No freeform intent parser is required. Optional later syntax sugar must map recognized tokens to visible filters; unknown words remain search terms.
- Establish an exact supported translation matrix against the production mailbox reader. A general/body search must not silently become View.thread.subjectContains.
- If a search cannot be faithfully represented, show unsupported clauses and permit refinement before saving.
- Save the complete query rather than a page of result IDs. Future matches appear automatically.
- Cancel preserves search context; empty results, failure/retry and naming remain recoverable.

Prototype search is explicitly subject-only; it does not prove production search equivalence. Validate equivalence across pages/accounts and future mail, independent of any AI runtime.

BRE-385 · Make view corrections and customization simple

Own saved-view edit, rename, reorder, removal, and deterministic correction presentation. Use the shared draft and preserve every unchanged advanced filter. This no longer depends on BRE-382.

- Let users change subject/senders/read state with labeled controls, see results, and undo the latest draft refinement.
- Correcting a match can offer a positive sender restriction with an explicit consequence: keeping the other known senders also excludes new senders until added.
- Disable that narrowing option when no other sender remains; do not accidentally turn an empty allowed set into “all senders.”
- Do not advertise semantic rental/client classification or conversational edits.
- Current schema has no general thread/sender exclusion. If the design selects true exclusion, implement bounded account-aware schema/evaluator/cursor support before exposing it; never fake it with static membership.
- Rename edits the same view; order persists; remove leaves mail intact. Draft cancel preserves the saved view.
- Names and grouping stay customizable; Save introduces no notification/routing policy.

Validate correction scope, undo/cancel, revision conflict, advanced-definition round-trip, lifecycle and both-theme controls.

BRE-386 · Teach organization through search and selected senders

Own the skippable first-view invitation, dismissal preference and reopen-help entry.

- Offer two starts: Search mail and Use selected mail. Reuse production preview/refinement/save throughout.
- Teach only the next action and show the saved result; no filter taxonomy tour, Describe it, assistant toggle, or agent setup.
- Persist dismissal at the scope chosen in BRE-380. Reopening never duplicates views.
- Empty mailboxes use clearly labeled examples; people can skip and return later.
- No automatic view creation or notification permission prompt.

Validate first visit, dismiss/reopen, both entry paths, empty mailboxes and subsequent visits. Capture each flow in both themes.

BRE-387 · Validate effortless search and sender-based view creation

Own uncoached usability evidence, repeatable fixtures and the HTML release guide. AI is not part of M9 acceptance and BRE-382 is not a dependency.

- Run the owner-approved protocol: search→preview→save; selected senders→preview→save; correction→undo; rename/retrieve; removal without mail changes.
- Proposed target for review: at least 4/5 participants independently create a useful view within 60 seconds and correct a wrong match. Report observed confusion and preview latency separately.
- Validate production search/view equivalence, future matches, account isolation, unchanged policies, concurrency/retry and advanced-view compatibility.
- Verify keyboard, default/hover/focus/pressed/disabled/loading/error controls in Light and Orca Black at 1440×900 and 1024×768.
- Run appropriate workspace checks and attach results and screenshots to an HTML guide.

Prototype evidence uses six sample messages and in-memory saves. It proves interactions can be exercised, not production persistence, actual mailbox semantics, authorization or human usability. Keep M9 open until its production acceptance evidence exists.

Small model on Railway?

Technically plausible: Railway supports CPU-compatible inference workloads. Qwen3 0.6B's quantized artifact is 523 MB; runtime RAM is additional. Neither fact establishes accurate filtering or interactive latency.

Recommendation: defer to BRE-382, now outside M9. Benchmark request-to-filter accuracy, clarification behavior, latency, memory and cost under concurrency before choosing a runtime. Hosting in Railway is server-side inference, not on the user's device. No infrastructure has been deployed.
