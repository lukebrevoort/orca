Attention routing: backend foundation

Actual local Inbox/Quiet routing is separate from notification intent. New callers share one account-scoped, revision-guarded API. No provider archive/delete operation is performed.

Effective precedence
Conversation override → exact sender rule → domain rule → explicit account default → Inbox (normal)

Read & manage

GET /v1/attention/routing?accountId=A
GET /v1/attention/routing?accountId=A&address=maya%40example.com
GET /v1/attention/routing?accountId=A&threadId=T

Response is AttentionRoutingState. senders includes all existing account rules, both address and domain, preserving legacy behavior and metadata. It is the complete configured-rule list, not the known-sender directory. Conversation selection derives inheritance from the latest stored message (received time, created time, then ID). Read with either an address or thread ID; thread ID takes precedence if both are provided.

{
  "accountId": "A", "revision": 7, "defaultBehavior": null,
  "senders": [],
  "selection": {
    "target": {"scope": "conversation", "threadId": "T"},
    "explicitBehavior": "quiet",
    "effective": {"behavior": "quiet", "destination": "quiet", "source": "conversation", "rule": null},
    "inherited": {"behavior": "normal", "destination": "inbox", "source": "fallback", "rule": null}
  }
}
FieldMeaning
defaultBehaviornull means no explicit default, retaining Inbox. This is independent of notification default quiet.
explicitBehaviorExact setting at the selected scope; null means inherit.
effective / inheritedCurrent result / result after clearing this scope. Source is conversation, sender, domain, account, or fallback.
destinationinbox for normal; quiet for quiet; null for notify, focus, hidden. Show the actual advanced behavior, never label these as Inbox/Quiet.
ruleFull matched sender/domain rule when one supplies the resolution.

Save, reset, Undo

PUT /v1/attention/routing?accountId=A
{
  "expectedRevision": 7,
  "target": {"scope": "conversation", "threadId": "T"},
  "behavior": "quiet"
}

Targets: {scope:"account"}, {scope:"sender",address:"maya@example.com"}, {scope:"conversation",threadId:"T"}. Send normal for Inbox, quiet for Quiet, or null to reset only the selected scope. Sender targets also accept existing advanced values so an inverse can restore an advanced exact sender choice.

{
  "state": {"accountId": "A", "revision": 8, "...": "canonical state"},
  "undo": {
    "expectedRevision": 8,
    "target": {"scope": "conversation", "threadId": "T"},
    "behavior": null
  }
}

Send the returned undo object using PUT to the same account URL. It restores the prior explicit behavior, or removes the newly created setting. Any later account routing change makes old Undo fail with HTTP 409. Do not automatically fetch a new revision and replay stale intent. Refresh canonical state and let the user choose again. Same-state saves with the current revision are no-ops; an old revision after a real write remains a conflict, even if desired behavior now matches. This avoids stale retries overwriting newer intent without adding history infrastructure.

Errors: 401 unauthenticated, 400 invalid payload, 404 unknown/foreign account or conversation, 409 stale revision. New frontend callers should exclusively use this interface for destination changes, key local state by account and sender/thread, then refresh affected mailbox/reader data. Never treat a local optimistic cache as persisted truth.

Known-sender lookup

GET /v1/attention/senders?accountId=A&query=maya
{
  "accountId": "A",
  "candidates": [{"address":"maya@example.com","name":"Maya"}],
  "truncated": false
}

Searches stored email senders and contacts by name/address; normalized address deduplication, deterministic address order, maximum 30 candidates. If truncated, ask the user to narrow the search. Candidates do not create rules. Search uses a bounded response, not a mailbox download; its database scan remains proportional to stored account mail/contacts.

Compatibility & boundaries

  • Legacy CRUD and resolve endpoints now accept optional accountId. Omission retains first-Gmail-account behavior. Batch remains account-targeted. Existing payloads are preserved.
  • Legacy unconditional writes intentionally retain legacy semantics. Database triggers advance the account routing revision after every sender rule insert/update/delete, so those writes invalidate in-flight new guarded saves. Legacy writes themselves are not protected against stale clients.
  • Mailbox filtering, counts and keyset pagination resolve routing in SQL before LIMIT. New defaults/overrides and resets invalidate mailbox cursors.
  • Reader returns optional additive thread.attention.attentionBehavior and per-message attentionBehavior. Thread aggregate uses latest sender; without a conversation override individual messages can retain different sender-derived behaviors.
  • Organization queries receive the same effective behavior. Lane placements, lane policies, safety/authority, classification, and provider labels are unchanged. Inbox/Quiet choices are attention behaviors, not Organization lane placements.
  • /v1/attention/preferences still reports delivery: proposal_only. There is no alert delivery service.
